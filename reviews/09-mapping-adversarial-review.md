## 一、总体结论

原稿最有价值的部分是“P0 不扩系统、P1 再做内容、P2 才做分布式”的分层，以及把修仙名词落到真实取舍上的意图。它不适合直接转为开发任务，原因不是方向错，而是三类证据还不够：

1. **事实不一致**：同一阶段、同一周期和同一试炼目标在源文档里存在冲突。
2. **映射过强**：多个 B/C 级类比被写成现实系统的等价物，会教授错误概念。
3. **验收不足**：P1/P2 多数只有玩法和名词，没有“什么情况应停止”的判据。

三轮审查后，建议维持原路线，但将“真实等价”统一降为“机制、部分模拟、叙事类比”三级，并把所有新增机制压到一个可回滚纵切。

## 三、第二轮：机制与概念准确性

### 3.1 发现

| ID | 严重度 | 原映射问题 | 后果 |
|---|---|---|---|
| R2-1 | **阻断** | “吐纳 = Event Loop / 轮询” | 把动作、固定步长调度和浏览器事件机制混成一件事 |
| R2-2 | **阻断** | “循环 = 批处理” | 循环只是重复控制流；批处理还需要窗口、输入集合和聚合 |
| R2-3 | **阻断** | “渡劫 = 压力测试 / 灰度 / 变更验证” | 随机成功率没有测试程序正确性、负载或变更质量，教学结论不成立 |
| R2-4 | **阻断** | “玉简 = 真实缓存” | 当前命中会改变产出，只免动作指令成本，缓存键也仅为 `actionId`；这是缓存成本模拟，不是严格缓存 |
| R2-5 | **阻断** | “指令步数 = CPU Cycles” | VM 逻辑指令数与物理周期没有换算关系 |
| R2-6 | 高 | “冲关 = 自动扩容” | 当前没有负载驱动扩缩容，只有阈值和就绪条件门控 |
| R2-7 | 高 | “蓄势 = Backoff / Batch Window” | 当前是墙钟就绪条件，不是错误率退避或批次窗口 |
| R2-8 | 高 | “离线 = Batch Job” | 当前是同一程序快进并施加游戏系数，还关闭部分风险与随机事件 |
| R2-9 | 高 | “心魔 = 技术债 / 错误预算 / 资源压力” | 当前只记录动作与循环风险，没有代码复杂度、错误率或机器资源模型 |
| R2-10 | 高 | “走火 = OOM / Thrashing / 级联故障” | 没有内存、换页或依赖故障模型，最多是风险预算越界 |
| R2-11 | 高 | 一个现实概念被多个修仙名包装，一个修仙名又覆盖多个现实概念 | 玩家无法建立稳定映射，后续内容也容易继续发散 |
| R2-12 | 中 | 指标只给名称，没有分母、缓存键、统计窗口或因果解释 | “命中率上升”“吞吐上升”可能成为不可比较的口号 |
| R2-13 | 中 | 原文的“加入玉简 → 单次产出下降”等示例没有说明循环与跳转仍有成本 | 容易把总步数节省误算成整段执行免费 |

### 3.2 关键修正

| 原稿 | 优化稿 |
|---|---|
| 炼气吐纳 = Event Loop / 轮询 | 每 tick = Fixed-step Scheduler；吐纳 = Periodic Job |
| 循环 = Batch | 循环 = Loop；Batch 只有具备窗口和聚合后才能成立 |
| 渡劫 = Stress Test | P0 渡劫 = Chance-based Risk Gate；测试型放行另立提案 |
| 玉简 = Real Cache | 玉简 = Cache-cost Simulation；机制 A、概念 B |
| 算盘 = CPU Core / vCPU | 算盘 = Compute Quota / Instruction Budget |
| 指令步数 = CPU Cycles | 指令步数 = VM 逻辑指令数，不等同真实耗时 |
| 离线 = Batch Job | 离线 = Catch-up Simulation |
| 境界 = Architecture Maturity | 境界 = Progression Tier，不评价算法或架构成熟度 |

本轮还补上了 P1 候选的机制前提，例如：

- 沙漏没有批次启动成本或排队延迟，就只是改变结算显示时间；
- 储物袋没有可保存的中间对象和淘汰策略，就只能退化成一个百分比；
- 丹炉没有语义等价的优化器，就会变成隐藏的产出倍率；
- 阵修没有任务、数据边和通信成本，就不能宣称 DAG 或分布式。

## 四、第三轮：工程实施与产品风险

### 4.1 发现

| ID | 严重度 | 发现 | 风险 |
|---|---|---|---|
| R3-1 | **阻断** | P1 进入条件没有覆盖存档、回放、内容版本和回滚 | 新机制可能破坏旧档，或让 Benchmark 无法复现 |
| R3-2 | **阻断** | P2 没有多节点仿真、通信成本或故障注入，却先给了大数据映射 | 最终可能只是把名称换成修仙词 |
| R3-3 | 高 | 没有为每个映射定义“决策指标 + 成本指标” | 机制可能只增加数字，不增加可学习的取舍 |
| R3-4 | 高 | 原稿教育闭环中的“玩家愿意再改一次”不可直接验收 | 容易把主观印象当成学习效果 |
| R3-5 | 高 | 没有单一种子与种子矩阵的分工 | 单种子演示可复现，但不能证明结论稳定 |
| R3-6 | 高 | 没有 Mapping ID、机制来源和版本证据链 | 改数值或内容后，旧教学结论会继续被误用 |
| R3-7 | 高 | 缺少每个纵切的 no-go 条件 | 团队容易用“已经做了一半”继续投入弱机制 |
| R3-8 | 中 | 缺少 P1/P2 的默认关闭与存档隔离要求 | 实验结果可能污染正式玩家进度 |
| R3-9 | 中 | 目标用户与学习验证任务未定 | 无法判断是教学失败还是用户不匹配 |

### 4.2 本轮优化

- 增加 G0–G4 阶段闸门，分别检查口径、观测、学习、P1 纵切和分布式真实性。
- P1 新增机制必须默认关闭，并具备独立存档命名空间或版本迁移、回放和卸载方案。
- 教育验证改为“预测 → 操作 → 解释 → 再修改”的任务，不做强制答题。
- Benchmark 使用演示单种子、验证种子矩阵分开的口径。
- 每个映射增加 Mapping ID、等级、机制来源、指标、边界、阶段和证据字段。
- 为 P2 增加“不得映射”清单，明确数据质量、Quorum、容错等当前不能凭名称成立。
- 文档最后明确：在 G0 完成前不转成编码任务。

## 五、三审后的最终判断

### 5.1 可以保留

- 固定步长调度、循环、分支、比较、预算和 stall 的 A 级映射；
- 玉简、心魔、调息、渡劫、蓄势、离线的边界化解释；
- P0 观测面板作为解释工具；
- P1 候选池与“一次只做一个纵切”的控制方式。

### 5.2 必须降级

- 真实缓存 → 缓存成本模拟；
- 压力测试/变更验证 → 随机风险闸门；
- 自动扩容 → 阈值门控；
- Backoff → 就绪等待；
- Batch Job → 快进结算；
- 技术债/OOM/Thrashing → 风险累积与强制停火；
- 架构成熟度 → 成长层级。

### 5.3 继续暂缓

- 多路线同时立项；
- 八阵并行开发；
- 无通信成本的多节点并行；
- 无故障模型的容错、Quorum 和 Autoscaling；
- 只靠倍率或视觉换皮的法宝与职业。

## 六、仍未解决、需要设计方拍板

1. `00-contracts.md` 的冻结状态与蓄势周期必须先统一。
2. 金丹试炼目标必须指定唯一值。
3. “试炼”“试炼场”“性能面板”的产品边界必须确认。
4. 渡劫究竟教“风险接受”还是“测试放行”，必须二选一或分成两个系统。
5. P1 第一纵切应在沙漏和丹炉中选一个，不能同时做。
6. 路线先做一条；第二条需通过 Pareto 差异验证。
7. 学习验收的目标人群、预测任务、解释任务和阈值需在实验前冻结。
