# 承雷反馈与「三次必成」修复方案（2026-11-26 下午）

> 玩家反馈两件事：
> 1. **承雷节奏反馈不够、视觉冲击不够强**；
> 2. **连续三次渡劫失败，运气太差**。
>
> 第 2 条先查代码：`attempt`（同一境界第 N 次）只活在内存，`restore()` 时写死 `attempt = 1`。也就是说**刷新一次，保底计数清零**。契约 §7.1 的本意是「同一境界连续挑战 3 次，第 3 次必成」，代码把「连续」错解成「不刷新」。这是本次要修的真问题，不是运气。

## 一、现状诊断

| 问题 | 根因 | 严重度 |
|---|---|---|
| 连败三次没保底 | `attempt` 只在内存：`runtime.restore()` 写死 1；HUD 也写「刷新清零」 | P1（玩家已实际踩到） |
| 不知道当前成功率 | 面板只显示心魔，没有把 `parryRate` 算给玩家看 | P1（反馈） |
| 命中/漏雷没有冲击 | 命中只让心魔条数字变一下、雷点变 ✓；漏雷要到结算才出现 ✗ | P1（反馈） |
| 节奏没有「倒数」 | 只有一行 12px 的「下一波 1.4s」 | P2 |
| 失败结果层只写「可再来一次」 | 没告诉玩家「下一发保底」 | P2 |

## 二、设计

### 1. 保底跨刷新（元进度，不动 GameState）

- 新 key：`gongfa:pity:<slot>`，值 `{ realm: number, attempt: number }`，只存 `attempt > 1`。
- 启动时：若 `pity.realm === 当前 realm` 且 `1 < attempt ≤ 3`，`runtime.restoreAttempt(attempt)`。
- 运行时：`attempt` 变化就写/清（成功、换境、清档都清）。
- 契约 §7.1 补一句：attempt 由元进度保存，刷新不清零；draw 索引仍按本境界第 N 次。
- 不动 `GameState`/schema v1，不碰存档结构；改档把 attempt 改成 99 也不会绕过（clamp 1..3，第 3 次本来就必成，改大只会更早触发保底）。
- HUD 文案「刷新清零」→「本档记录」；第 2 次失败后提示「再失败一次，下一发必成」。

### 2. 承雷的「可读反馈」

面板从上到下改成：

```
渡劫 · 炼气 → 筑基            成功率 84%
[心魔条 ▓▓▓░░]  [雷点 ● ● ●]  [10s 进度条]
        下一波 1.4s · 承雷窗口 ±700ms
[ 承雷 ]  [ 交给天意 60% ]
```

- **成功率**：`parryRate({ hits, misses: 当前已漏波数, demon })` 现算，大号显示；颜色 ≥85 青 / 60–85 金 / <60 朱。
- **雷点**：三盏灯按波次（上一轮已修）；下一波加 `.is-next` 脉冲与倒数；命中后留 ✓，漏了留 ✗。
- **进度条**：0→10s，三个刻度对应 2/5/8s，光标随 `elapsedMs` 前进。
- **命中反馈**：青色全屏闪光 + 面板轻微震动（180ms）+ 扩散环 + 飘字「承雷 +2%」+ 心魔条脉冲。
- **漏雷反馈**：朱红全屏闪光 + 更强震动 + 飘字「漏雷 −5%」+ 雷点变 ✗。
- **进窗口**：三盏灯依次亮一次（400ms 内），提示「三波雷 2/5/8s」。

### 3. 数据面

`RuntimeState.trialParry` 增加：

```ts
readonly rate: number;       // 当前投影成功率（parryRate）
readonly elapsedMs: number;  // 进窗口后的毫秒
```

`settle` 的结算口径不变（仍是 10 秒到期按 hits/misses 算）。

### 4. 失败结果层

- 失败时若 `attempt + 1 >= 3`：结果层副标加「下一发保底必成」。
- 否则：`存量 ×0.85，心魔归 0，可再来一次（第 N 次 · 再失败 M 次必成）`。

## 三、三遍对抗性审查

### 第一遍：会不会改坏渡劫本身？

| 质疑 | 结论 / 处置 |
|---|---|
| 存 pity 会不会让「第 3 次必成」变成「永远必成」？ | 只在 `attempt === 3` 时 forced；成功后 `attempt=1` 并清 pity；换境清；清档清 |
| 刷新后 `attempt=3`，但玩家换了一个境界呢？ | 读取时校验 `pity.realm === 当前 realm`，不匹配就忽略 |
| 改档把 attempt 写成 0 / 99 呢？ | `restoreAttempt` clamp 到 1..3；0/负数回 1，≥3 记 3（第 3 次必成，不额外送） |
| 存 pity 会不会和 draw 索引冲突？ | draw 仍用 `seed + 1_000_000 + N`；N 跨刷新一致，同一次尝试的骰值不变，反而更可复现 |
| 失败后 qi ×0.85 掉回阈值下，还能继续攒吗？ | 能，蓄势不清零；本方案不动 |
| 加 `rate` 字段会不会进存档？ | `trialParry` 是派生字段，GameState 无它 |
| 闪光/震动会不会挡住「承雷」按钮？ | FX 层 `pointer-events:none`，按钮 z-index 更高；震动用 Web Animations 只改 transform，不改布局 |
| 锚点：settlement 会不会被 FX 的 state 更新拖慢？ | FX 只在 hits/misses/waves 变化时 setState 一次，不是每帧 |

### 第二遍：玩家真的会觉得「公平/有冲击」吗？

| 质疑 | 结论 / 处置 |
|---|---|
| 成功率一直显示，会不会让 85% 显得「太稳」？ | 显示的是**当前档**：漏一波立刻掉到 80%，玩家能看到自己把概率打没了；这正是要的反馈 |
| 震动/闪光太吵？ | 震动 180ms、闪光 420ms；`prefers-reduced-motion` 下全部关闭，只保留数字与颜色 |
| 手机上 FX 会不会卡？ | FX 是 1 个绝对定位层 + CSS 动画，不给 15 个块加滤镜；390 档截图与帧时间验证 |
| 失败结果层说「下一发必成」会不会反而像作弊？ | 契约本来就是第 3 次必成，说出来比藏着好；保底仍只触发一次 |
| 保底跨刷新会不会让「连败」失去紧张感？ | 玩家仍要经历 2 次失败；第 3 次是契约承诺的兜底，不是白送 |
| 如果玩家在第 2 次失败后换档呢？ | pity 按槽隔离，换档不串 |

### 第三遍：工程与回归

| 质疑 | 结论 / 处置 |
|---|---|
| 新增 meta key 要不要迁 schema？ | 不要，元进度按 §9 的先例（`gongfa:found:<slot>`）走，不进 GameState |
| 清档能不能清掉？ | `resetAllSaves` 走 `gongfa:` 前缀，覆盖 |
| 老玩家没有 pity key？ | 读不到就是 null，attempt 从 1 起，和现在一致 |
| StrictMode 双挂载会不会把 pity 写两次？ | 写是幂等的；启动读取只做一次 restoreAttempt |
| 测试怎么写？ | `pity.ts` 纯函数单测；runtime `restoreAttempt` clamp 单测；三次连续失败必成的 runtime 测试（假时钟）；E2E「失败一次 → 刷新 → HUD 仍显示第 2 次」 |
| 视觉改动会不会打断已有 E2E 选择器？ | 保留 `.trial-wave.is-hit/.is-miss`、`.trial-parry`、`.trial-demon-value`；新增 `.trial-rate`、`.trial-fx`、`.trial-pop` |
| 回退路径？ | 视觉在 CSS/组件；pity 在独立 `pity.ts` + 一处 restore + 一处 sync；可单独 revert |

## 四、执行顺序

1. `pity.ts` + 单测；runtime `restoreAttempt` + 三次必成测试。
2. App 启动读取 / 帧内同步 / 清档；
3. `trialParry` 增 `rate`/`elapsedMs`；
4. TrialPanel 重排 + FX + CSS；
5. HUD 文案（第 2 次失败提示、结果层「下一发必成」）；
6. typecheck/test → E2E（承雷全中/漏/失败刷新）→ build → 推送 → 线上截图。
7. 更新 `reviews/22`、契约 §7.1、HANDOFF。
